## 一句话理解

> 推荐系统里的 **item** = **你要推的"那个东西"**。
>
> **物品理解 = 给 item 做"身份证"**——让算法从"看到一串 ID"升级到"看懂它是什么"。
>
> 没有身份证的人 = 一个面目模糊的陌生人 → 算法只能"看脸色"硬猜（协同过滤）。
>
> 有了身份证 = 算法知道他叫啥、长啥样、做什么工作、什么时候出生 → 才能做**真正聪明的推荐**。

## 1. Item 是啥 — 不同平台不同物种

| 平台 | item 是什么 | 具体内容 |
|---|---|---|
| **抖音 / 快手** | 一段短视频 | 60s 内、含 BGM、字幕、特效 |
| **TikTok** | 一段短视频 | 同上，多语种 |
| **YouTube Shorts** | 一段 60s 短视频 | 跟主站 YouTube 算法独立 |
| **YouTube 主站** | 一段长视频 | 1 分钟到几小时 |
| **小红书** | 一篇笔记 | 图 + 文 + 话题 + 商品链接 |
| **Pinterest** | 一个 Pin | 图片 + 描述 + 落地页 |
| **网易云 / Spotify** | 一首歌 | 音频 + 歌词 + 元数据 |
| **淘宝 / 天猫** | 一个 SKU | 商品 + 价格 + 详情页 |
| **Booking** | 一家酒店 | 地理 + 价格 + 评价 |
| **滴滴** | 一对司机+车型 | 实时上线的司机 |
| **美团** | 一家餐厅或一个团购套餐 | 商家 + 优惠 |
| **MovieLens** | 一部电影 | ID + 标题 + 类型 |

→ **item 千变万化，但都是"被推的那个东西"**。

> **共同的关键观察**：**真实业务里的 item 都是多模态的复杂物体**，而 ML-1M 只有 ID + 标题 + 类型，是个"残疾版"——很多物品理解的方法在 ML-1M 上压根用不上。

## 2. Item 的 4 个面 — 一张完整的身份证

每个 item 都有 4 个面，就像你的身份证：

| 面 | 身份证类比 | item 上的含义 |
|---|---|---|
| **ID 面** | 身份证号码 | item_id，唯一标识 |
| **内容面** | 姓名、性别、照片 | 标题、描述、图片、视频帧、音频 |
| **统计面** | 被查过几次（背后的查档记录） | 累计播放、点赞、评论、CTR、完播率 |
| **时间面** | 签发日期、有效期 | 发布时间、热度衰减、过期标记 |

### 一个具体例子：一段抖音美食视频

```
ID 面：
  item_id = v_8973261

内容面：
  标题: "10 分钟教你做完美红烧肉，新手友好"
  封面: [一张红烧肉的图]
  视频帧: 厨师切肉 → 焯水 → 翻炒 → 出锅
  字幕（ASR）: "今天教大家做红烧肉，五花肉先焯水..."
  音频: BGM "成都" + 厨师讲解
  话题: #家常菜 #红烧肉 #下饭神器

统计面:
  播放量: 12 万次
  点赞: 8,300
  评论: 256
  完播率: 47%
  分享: 412
  CTR (推荐位): 4.8%

时间面:
  发布时间: 3 小时前
  生命周期: 24h 内 70% 流量会消耗完
```

→ 这 4 个面**缺一不可**。少一个面，模型对它的理解就有盲区。

## 3. 为啥不能只看 ID

**关键问题**：新视频 `v_8973261` 这个 ID 模型**从没见过**，协同过滤算法**完全无从下手**。

```
ItemCF：
  "我得知道'谁还看过 v_8973261'，才能找到相似的视频"
  但是 v_8973261 刚发 3 小时，几乎没人看过
  → ItemCF 瞎了

双塔（如果只用 ID 训练 item embedding）：
  "v_8973261 这个 ID 在训练集里没出现过"
  → embedding 是随机的、没意义的
  → 双塔也瞎了
```

**只看 ID 的推荐 = 只能推熟悉的老朋友**。

**看了内容面**：
```
即使是新视频，模型能看到：
  视觉特征 → "这是一段做菜视频"
  ASR → "讲的是红烧肉"
  标签 → #家常菜 #下饭神器
→ 找跟"做菜 + 红烧肉 + 家常菜"相似的存量视频 → 借它们的目标用户
```

**这就是物品理解的根本价值**：**让模型不依赖 ID 也能推**。

## 4. Item 和 User 是镜像兄弟

很巧的是，user 也有同样的 4 个面：

| 面 | item | user |
|---|---|---|
| ID 面 | item_id | user_id |
| 内容面 | 标题/图/视频/标签 | 性别/年龄/职业/兴趣标签 |
| 统计面 | 总播放/CTR/完播率 | 总浏览量/总互动率/活跃天数 |
| 时间面 | 发布时间/生命周期 | 注册时间/上一次活跃 |

**所以**：

- **双塔模型**为啥叫"双塔"？因为 user 塔和 item 塔**对称结构**——4 个面都对应建模
- **"用户理解"和"物品理解"是镜像问题**——技术栈基本一致

## 5. 为啥业务一定要理解 item — 5 个理由

| 业务诉求 | 物品理解怎么帮 |
|---|---|
| **解决新物品冷启** | ID 没数据 → 用内容面找相似存量物品借用户 |
| **多样性控制** | 知道这条是"美食"、那条是"穿搭"→ 不让全屏单类目 |
| **质量与风险过滤** | 用 embedding 识别盗图、AI 生图、低俗、暴力 |
| **可解释性** | "因为你喜欢《盗梦空间》，推《信条》（同导演）" |
| **跨场景迁移** | 抖音学到的视频理解能力 → 用到 TikTok、抖音电商、抖音直播 |

## 6. recsys-mini 里的物品是啥样

ML-1M 的电影 item 是这样的：

```
MovieID = 1
Title   = "Toy Story (1995)"
Genres  = "Animation|Children's|Comedy"
```

仅此而已。**没有海报、没有剧情简介、没有演员表、没有导演**。

| 完整身份证 | recsys-mini 实际有 |
|---|---|
| ID 面 | ✓ MovieID |
| 内容面（强大版） | **半残**：只有 Title + Genres，没图、没视频、没音频 |
| 统计面 | ✓ 可以从 ratings 算（被几个人评过、平均分） |
| 时间面 | **几乎没有**：Title 里有年份（1995），但没有发布时间戳 |

→ **ML-1M 几乎只能做最基础的物品理解**：
- 用 Title 做 word2vec → 找名字相似的电影
- 用 Genres multi-hot → 简单倒排召回

→ 想做**真正的多模态物品理解**，必须切到 **KuaiRand**（含视频/音频特征）或 **MIND**（新闻推荐，含丰富文本特征）。

## 7. Item 理解的 4 种输出形式

物品理解的最终产出有 4 种形式：

| 输出 | 例子 | 用途 |
|---|---|---|
| **Tags（标签）** | `#家常菜`, `#红烧肉`, `category=美食` | 倒排召回、用户兴趣对齐、人工运营 |
| **Embedding（向量）** | `[0.12, -0.43, 0.78, ..., 0.05]` 共 128 维 | 双塔召回、ANN 检索、相似度计算 |
| **Scores（分数）** | `quality=0.85`, `risk=0.12`, `predicted_ctr=0.045` | 过滤、排序加权 |
| **Relations（关系/KG）** | `诺兰 - 执导 - 《盗梦空间》` | KG 召回、可解释推荐 |

> **4 种形式不是互斥的**，往往一个 item 同时拥有这 4 种产出。

## 8. 多模态 — 怎么把一条视频"拆开看"

**核心思路**：一段视频不是"一团数据"，而是**多个模态**的合体——视觉 + 音频 + 文本，**每个模态都用一个专门的模型抽特征**。

### 抖音美食视频的拆解流水线

```
原视频 v_8973261
    │
    ├─────────────────────────────────────┐
    │                                       │
    ▼                                       ▼
┌──────────────────────┐         ┌──────────────────────┐
│  视觉模态 (CV)        │         │  音频模态 (Audio)     │
│  - 视频帧采样          │         │  - ASR 抽字幕         │
│  - SlowFast / R3D     │         │  - 音乐识别（"成都"） │
│  - 输出: 视觉 emb 512d │         │  - 情绪识别（"激动"） │
└──────────────────────┘         └──────────────────────┘
    │                                       │
    └────────────────┬──────────────────────┘
                     ▼
            ┌──────────────────────┐
            │  文本模态 (NLP)       │
            │  - 标题 + 字幕 + 话题 │
            │  - BERT / Chinese RoBERTa
            │  - 输出: 文本 emb 768d │
            └──────────────────────┘
                     │
                     ▼
            ┌──────────────────────┐
            │  融合模态 (Multi-modal)│
            │  - 拼接 / Attention    │
            │  - 输出: 总 emb 128d   │
            └──────────────────────┘
                     │
                     ▼
              用于召回 + 排序
```

### Pinterest 对一张穿搭图的处理

```
一张穿搭 pin
    │
    ├── SearchSage (Pinterest 自研视觉模型) → 视觉 embedding
    ├── OCR 识别图中文字 → 字段抽取（品牌、价格、尺码）
    ├── NLP 抽 description 里的 tags → "韩系" "通勤" "秋装"
    ├── Color extraction → 主色调
    └── 内容分类 → "Fashion > Women > Outerwear"
    
→ 综合形成 Pin 的多模态向量 + 标签 + 类目
```

### 小红书对一篇笔记

```
一篇笔记
    │
    ├── 图（最多 9 张）→ 视觉 embedding（每张 + 整体）
    ├── 文 → NLP embedding + 关键短语抽取
    ├── 话题 → multi-hot
    ├── 商品 → SKU 链接 → 跟商品图谱挂钩
    └── 评论 → 情感分析 + 关键词
    
→ "种草强度评分"、"购买意向预估"
```

→ 多模态理解的本质：**让模型能"看到"+"听到"+"读到"item 的全貌**。

## 9. 结构化理解 — 标签 / NER / 知识图谱

### 9.1 标签体系 — 多层级结构

```
一级（10-20 个）   →  美食
                       │
二级（100-200 个）  →   ├── 家常菜
                       │   │
三级标签（1k-100k）   │   ├── 红烧肉
                       │   ├── 番茄炒蛋
                       │   └── ...
                       │
                       └── 国际料理
                           ├── 意大利面
                           └── ...

四级实体（百万级）   →  红烧肉做法、五花肉品牌、特定厨师...
```

→ **每一层负责不同业务**：一级看用户兴趣分布，二级做召回，三级做精细推荐，四级做垂类推荐。

### 9.2 NER（命名实体识别）

> "从标题/描述中抽取人名、地名、品牌名、产品名"

```
原文: "今天去了上海外滩的星巴克"
NER 抽取:
  - 地点: 上海、外滩
  - 品牌: 星巴克
```

→ 这些实体可以**直接做倒排召回**：用户搜"星巴克" → 调出所有标注了"星巴克"的笔记/视频。

### 9.3 知识图谱（KG）

> "把 item 串成一张关系网"

**电影 KG 示例**：

```
《盗梦空间》 ─── 执导 ───► 诺兰
       │                     │
       └─── 主演 ──► 迪卡普里奥  │
                        │     │
                        └── 主演 ───► 《泰坦尼克号》
                              │
                诺兰 ── 执导 ───► 《信条》
```

**应用**：用户喜欢《盗梦空间》→ 模型沿着"诺兰→《信条》"、"迪卡普里奥→《泰坦尼克号》"两条边推荐。

**真实业务里的 KG**：

| 平台 | KG 形态 |
|---|---|
| **YouTube** | 视频 - 频道 - 作者 三元组 KG |
| **小红书** | 话题图谱（穿搭 → OOTD → 韩系穿搭 → 通勤穿搭） |
| **淘宝** | 商品 - 品牌 - 品类 - 店铺 KG |
| **网易云** | 歌曲 - 歌手 - 专辑 - 曲风 KG |

## 10. 质量与风险评估

**目标**：自动识别"该推" vs "不该推"的内容。

### 质量评估

| 维度 | 怎么做 |
|---|---|
| 画面清晰度 | 模糊度检测 |
| 画面稳定度 | 抖动度检测 |
| 内容完整度 | 是否有头尾、是否被截断 |
| 互动潜力 | 用 content-based 模型预估 CTR |

### 风险评估

| 风险 | 怎么识别 |
|---|---|
| 盗图 / 搬运 | **Pinterest 用 embedding 检索全网相似图** → 找到原图 |
| AI 生图 | **小红书用专门的 AI 鉴别模型** + embedding 异常检测 |
| 低俗 / 暴力 | 多模态分类模型（视觉 + 文本） |
| 假信息 | NLP 事实核查 + 信源信誉 |
| 引战 | 评论情感分析（高负面情绪 + 高互动） |

## 11. 工业级 backbone — 训练范式

### 三种主流训练范式

#### 11.1 自监督（self-supervised）⭐ 最主流

**思路**：不需要人工标注，让模型自己"出题考自己"。

| 模型 | 任务 |
|---|---|
| **BERT** | "遮一个词让模型猜"（masked language modeling） |
| **CLIP**（OpenAI）⭐ | "图文配对"——给一张图，从一堆文字里选出正确的描述 |
| **Wav2Vec**（Meta）⭐ | "遮一段音频让模型猜"（masked acoustic modeling） |
| **MAE**（Meta）⭐ | "遮一块图像让模型猜"（masked image modeling） |

→ **优势**：海量数据，不需要标注，效果直追监督学习。
→ **几乎所有大平台的 item 理解 backbone 都是自监督预训练 + 业务微调**。

#### 11.2 多任务监督（multi-task supervised）

**思路**：一个模型同时预测多个业务目标。

**小红书"种草决策"多任务**：

```
输入：item 多模态特征
输出（4 个 head 并行）：
  - 预估 CTR
  - 预估 CVR（购买转化）
  - 预估完播率
  - 预估评论意愿

Loss = Σ task_weight × task_loss
```

→ **同一份特征服务多个业务，效率高**。

#### 11.3 行为对齐（behavior-aligned）

**思路**：用真实业务行为反过来 fine-tune 内容 embedding。

```
预训练 CLIP → 通用图文 embedding（不针对业务）
↓ fine-tune
用平台"用户点击 / 完播"行为对 → 让 embedding 更适配业务
```

→ 这就是为啥**快手、抖音都在自研 backbone**——比如**快手开源的 KwaiYii / KwaiVision 系列**，**Pinterest 自研的 PinText / PinSage**。直接拿 OpenAI 的 CLIP 通用模型在业务上效果会**显著弱于**自研 backbone。

## 12. Item 理解的输出用在哪

物品理解的 4 种输出，**贯穿整个推荐管线**：

| 阶段 | 用 item 理解干啥 |
|---|---|
| **召回** | 双塔的 item tower 输入；内容相似召回；倒排召回 |
| **排序** | item embedding + tags + scores 全部作为特征喂给排序模型 |
| **过滤** | 用 quality / risk scores 提前剔除低质 / 高风险 |
| **重排** | 用 tags 做多样性控制（一屏不能 > 30% 同类目） |

→ **物品理解 = 整个推荐系统的"前置依赖"**。它的质量直接决定下游所有阶段的天花板。

## 13. recsys-mini 能做点啥

基于 ML-1M 的"残疾版"数据（只有 Title + Genres），能做：

| 任务 | 实现 |
|---|---|
| **电影名相似度召回** | `word2vec(Title)` → ANN → top-K 相似电影 |
| **类型倒排召回** | `Genres` multi-hot → 给每个类型维护倒排链表 |
| **类型多样性重排** | 召回结果按 Genres 分桶 → 强制每类目占比 |
| **可解释推荐** | "推荐《信条》因为它跟你看过的《盗梦空间》同导演（如果我们有导演数据的话）" |

**做不到的**（必须切数据集）：

| 任务 | 缺什么 | 推荐数据集 |
|---|---|---|
| 多模态融合 | 没有海报 / 视频 / 音频 | **KuaiRand**（含视频特征） |
| 实时 KG | 没有完整的演员/导演表 | **IMDB** + ML-1M 拼接 |
| 用户评论分析 | 没有评论数据 | **Amazon Reviews** |
| 大规模长尾 | 数据规模太小 | **MIND**（新闻）/ **KuaiRand** |

## TL;DR — 三句话

1. **Item 是你要推的"那个东西"**——抖音 = 视频，小红书 = 笔记，Pinterest = pin。
   **物品理解 = 给 item 做"身份证"**，让算法看懂它而不是只看到一串 ID。

2. **Item 有 4 个面**：ID / 内容 / 统计 / 时间。
   **内容面是冷启动的命脉**——多模态（视觉 + 音频 + 文本）是工业界标配。

3. **输出 4 种形式**：tags + embedding + scores + relations(KG)。
   **贯穿召回 / 排序 / 过滤 / 重排**——直接决定整个推荐系统的天花板。

## 一句话理解

> **热门召回 = 录像带店门口那块「本周热租榜」。**
>
> 它不管你是谁、看过啥，只干一件事：「**把全店租得最多的片，从高到低列出来。**」
>
> 当老挑片员（ItemCF）对你束手无策时——你是新客、没历史、或者她的账本恰好没覆盖到你——**热门榜小哥永远能甩给你一句**：「**那就先看看大家都在租的这些吧。**」
>
> **它是整个推荐系统里最简单、最便宜、却永远不会被淘汰的一路召回——因为它是兜底的"保险栓"。**

## Level 1：店门口的热租榜 — 什么是热门召回

回到那家开了 20 年的录像带出租店。

老挑片员（ItemCF）很厉害，但她有个毛病：**你得先有租赁历史，她才能给你推荐**。新客第一次进门、或者那种一年才来一次的稀客，她翻遍账本也算不出"铁哥们榜"。

于是店里还雇了个**热门榜小哥**。他的工作朴素到极点：

```
每周一早上，他翻一遍上周所有租赁单子，数一数：
  《阿凡达》   租了 560 次  ← 冠军
  《教父》     租了 480 次
  《好家伙》   租了 450 次
  《盗梦空间》 租了 420 次
  ...
然后把这个榜单抄在店门口的黑板上。
```

任何客人进门，只要老挑片员搞不定，热门榜小哥就指着黑板说：「**喏，大家都在租这些，你也看看？**」

### 热门召回的核心信念（一句话）

| 信念 | 通俗说法 |
|---|---|
| **从众即安全** | "**大多数人选的东西，大概率不会太差**" |

注意：热门榜小哥**完全不做个性化**。给张三和李四看的榜单**一模一样**（唯一的区别是各自跳过自己已经看过的）。这既是它的弱点，也是它的优点——**简单、稳定、永远有结果**。

## Level 2：别小看它 — 热门榜小哥的三个角色

很多人第一反应是"热门召回太简单了，有它没它无所谓"。**大错特错。** 它在系统里扛着三个谁也替不了的活：

### 角色 1：兜底（Fallback）—— 保证"永远有东西可推"

```
新客小白第一次进店
  → 历史 = []
  → 老挑片员：算不出来，返回空 []
  → 热门榜小哥：没关系，本周热租榜拿去！
```

**这是热门召回最重要的使命**：当所有个性化召回都返回空时，系统**绝不能给用户一个白屏**。热门榜就是那个"再差也有这个"的底线。

### 角色 2：冷启动（Cold Start）—— 新用户的第一印象

新用户还没产生任何行为，个性化模型无从下手。热门召回这时承担**"探路者"**的角色——先用大众爆款探一探他的口味，等他点了几下、攒出最初的几条历史，再逐步交给 ItemCF / 双塔接管：

```
新用户进来（历史 = []）
   │
   ▼  第 1 屏：纯热门（大众爆款，命中率最稳）
   │      用户点了《盗梦空间》《星际穿越》→ 攒出 2 条历史
   ▼  第 2~3 屏：热门占比下降，ItemCF 开始介入（"看了盗梦的人还看了…"）
   │
   ▼  历史足够后：个性化召回（ItemCF / 双塔）接管，热门退回兜底位
```

> 这背后是经典的 **探索-利用（Explore-Exploit）权衡**：完全推热门=只"利用"已知的安全选项，永远摸不清新用户的小众口味；适当掺入多样内容=花一点曝光去"探索"。热门召回是这场权衡里**最稳的起手式**——先用它保证不翻车，再慢慢让个性化接手。完整的冷启动策略（Bandit、look-alike、喜好问卷等）详见 [`02-cold-start_CN.md`](02-cold-start_CN.md)。

### 角色 3：保险栓 —— 给个性化召回"补底"

即使老用户，个性化召回也可能因为窗口太窄、覆盖不足而**凑不满 200 个候选**。这时热门榜小哥负责**把候选名单填满**，保证交给排序模型的候选数量充足。

> **一句话**：热门召回是推荐系统的**保险栓**——它单独跑指标平平，但**没有它，系统在冷启动和异常情况下会直接崩**。

## Level 3：怎么算"热度" — 从数人头到归一化

热门榜小哥算热度的逻辑，比老挑片员简单太多了。我们一步步看。

### 朴素版：数人头

```
某部片的热度  =  上周它被租了多少次
```

代码就一行 `groupby` + `size`：

```python
pop = train_df.groupby("item_id").size().sort_values(ascending=False)
```

- `groupby("item_id")`：把所有租赁记录按"片"分组
- `.size()`：数每组有多少条 → 每部片被交互的次数
- `.sort_values(ascending=False)`：从高到低排，最热门的排最前

得到一个按热度降序的榜单：

```
item_id
《阿凡达》    560   ← 冠军
《教父》      480
《好家伙》    450
...
```

### 升级：把热度归一化到 [0, 1]

光有原始次数还不够。**热门召回不是单独工作的**——它要和 ItemCF 等其他召回路一起，把候选交给排序模型融合。但各路召回的分数量纲完全不同（ItemCF 的"亲密度累加"可能上不封顶），**直接放一起没法比**。

所以热门榜小哥把所有热度**除以最高热度**，全部压到 `(0, 1]`：

```python
max_p = pop.iloc[0]          # 最热门那部的次数 = 560
score = float(c) / max_p     # 每部片 = 自己的次数 / 560
```

| 电影 | 原始次数 | 归一化分数 |
|---|---|---|
| 《阿凡达》 | 560 | 560/560 = **1.00** |
| 《教父》 | 480 | 480/560 = 0.857 |
| 《好家伙》 | 450 | 450/560 = 0.804 |
| ... | ... | ... |

> **为啥要归一化？** 和 ItemCF 是同一个理由——**便于多路融合**。每路召回都把自己最高分当 1.0，大家话语权对等，排序模型融合时才公平。详见 [`05-collaborative-filtering_CN.md`](05-collaborative-filtering_CN.md#为啥要把分数归一化到-0-1) 里"4 位挑片员打分"的例子。

## Level 4：热门召回的四个工程坑

"不就是按热度排序吗"——真这么想就要踩坑了。热门榜小哥 20 年下来也填了几个坑。

### 坑 1：马太效应 —— 越热越推，越推越热

> **什么是马太效应（Matthew Effect）？** = **强者愈强，弱者愈弱**（"富者越富"）。
>
> 名字来自《圣经·马太福音》里的一句话：
>
> > "凡有的，还要加给他，叫他有余；没有的，连他所有的也要夺去。"
> > （For to every one who has will more be given... but from him who has not, even what he has will be taken away.）
>
> 社会学家罗伯特·默顿（Robert Merton）1968 年用它来描述一种**正反馈循环**：已经占优势的一方，会因为这个优势获得更多资源，从而优势越来越大；劣势的一方则越来越被边缘化。

放到热门召回里，这个正反馈闭环就是：

```
《阿凡达》本来就红 → 被推到所有人面前 → 更多人租 → 下周更红 → 推得更凶...
                ↑________________________________________|
```

这是热门召回的**头号副作用**：它天然制造"赢者通吃"，让冷门内容**永无出头之日**。表现在指标上就是 **Coverage（覆盖率）极低**——recsys-mini 实测热门召回的 `Coverage@200` 只有 **22.29%**，意味着 78% 的电影**永远不会**出现在任何人的热门候选里。

> **解药**：① 控制热门召回的融合权重（recsys-mini 里 `popular: 0.3`，只有 ItemCF 的 0.3 倍）；② 靠内容召回 / Swing 等其它路去捞长尾。

### 坑 2：已看过的不能再推（已看过过滤）

榜单是全店统一的，但**每个人看过的不一样**。如果不过滤，会出现"把你上周刚租的《阿凡达》又推给你"的尴尬。

**热门榜小哥的解法**：给每个客户记一份"看过清单"，推荐时跳过：

```python
seen = self._user_history.get(user_id, set())
# ...遍历榜单时：if item_id in seen: continue
```

用 `set`（集合）存而不是 `list`，是因为 `in` 判断集合是 O(1)，列表是 O(n)——过滤要快。

### 坑 3：时效性 —— 榜单多久更新一次

```
某网红片周三突然爆火
  → 但热租榜是周一抄的
  → 这片还没进榜
  → 召不出来
```

热度是有**时效**的。榜单更新越频繁（小时级 > 天级 > 周级），越能抓住趋势，但计算成本也越高。recsys-mini 是离线一次性 `fit`，属于"静态热门"——够用，但抓不住实时趋势。

> 这个坑有两层解药，分别对应 Level 6 的两个升级款：① 让"老热度"自动降权 → [6.1 时间衰减热门](#61-时间衰减热门--最近火的更重要)；② 让榜单"秒级"跟上突发爆款 → [6.4 实时热门](#64-实时热门--秒级追上突发爆款)。

### 坑 4：用"次数"还是"人数"？—— 重复交互偏差

如果一个铁粉把《教父》反复租了 50 次，按"租赁次数"算，《教父》的热度会被一个人**严重灌水**——它的"热"其实只是"一个人很爱"，而不是"很多人爱"。

两种热度定义，一字之差，结果天差地别：

```python
# ① 数交互行数（recsys-mini 当前做法）——一个铁粉的 50 次重复也算 50
c_i = train_df.groupby("item_id").size()

# ② 数去重后的独立用户数——一个铁粉无论租几次都只算 1 票
c_i = train_df.groupby("item_id")["user_id"].nunique()
```

| 场景 | 推荐用哪个 | 为什么 |
|---|---|---|
| 评分 / 一次性消费（电影、商品） | ① 次数 | 每人对每物品基本只交互一次，两者几乎等价 |
| 可重复消费（音乐、短视频、新闻） | ② **独立用户数** | 防止"单人狂刷"把某个物品顶上榜，**"多少人爱"比"被播多少次"更能代表真热度** |

> recsys-mini 用的是 ① `groupby("item_id").size()`（数行数）。这在 ML-1M 上问题不大（评分数据每人每片基本只评一次），但如果换成可重复消费的数据集，应优先改用 ② `nunique("user_id")`。

## Level 5：recsys-mini 代码逐行走读

`src/recall/popular.py` 全文只有 36 行，把上面讲的逻辑全实现了。我们逐块拆。

### 5.1 类定义 + 两个"小本本"

```11:24:src/recall/popular.py
class PopularRecaller(BaseRecaller):
    name = "popular"

    def __init__(self, topk: int = 200):
        self.topk = topk
        self._top_items: List[Tuple[int, float]] = []
        self._user_history: dict[int, set[int]] = {}

    def fit(self, train_df: pd.DataFrame) -> None:
        pop = train_df.groupby("item_id").size().sort_values(ascending=False)
        # score 归一化到 [0, 1] 便于多路融合
        max_p = pop.iloc[0]
        self._top_items = [(int(i), float(c) / max_p) for i, c in pop.items()]
        self._user_history = train_df.groupby("user_id")["item_id"].apply(set).to_dict()
```

| 成员 | 类型 | 装的是 |
|---|---|---|
| `name = "popular"` | str | 召回器的"身份证"，多路融合时用它取权重 |
| `topk` | int | 榜单最多保留多少个（默认 200） |
| `_top_items` | `List[(item_id, 归一化分数)]` | **全局热门榜**，fit 时灌满，按热度降序 |
| `_user_history` | `dict[user, set[item]]` | 每个用户**看过的集合**，推荐时去重用 |

#### `fit` 在干啥（对应 Level 3）

1. `groupby("item_id").size().sort_values(...)` —— 数热度，降序排（Level 3 朴素版）
2. `max_p = pop.iloc[0]` —— 取最热门那部的次数当归一化分母
3. 列表推导式 —— 把每部片转成 `(item_id, 次数/max_p)`，归一化到 `(0, 1]`（Level 3 升级版）
4. `groupby("user_id")["item_id"].apply(set)` —— 给每个用户建"看过集合"（Level 4 坑 2 用）

> **关键设计**：和 ItemCF 一样，**重活全在 `fit` 时算好**，`recall` 时只查表遍历。离线慢没关系，在线必须快。

### 5.2 recall — 在线推荐

```26:35:src/recall/popular.py
    def recall(self, user_id: int, k: int) -> List[Tuple[int, float]]:
        seen = self._user_history.get(user_id, set())
        out: List[Tuple[int, float]] = []
        for item_id, score in self._top_items:
            if item_id in seen:
                continue
            out.append((item_id, score))
            if len(out) >= k:
                break
        return out
```

#### 逐行翻译

| 行 | 在干啥 | 注释 |
|---|---|---|
| `seen = self._user_history.get(user_id, set())` | 取这个用户"看过的集合" | **新用户取不到 → 默认空集 `set()` → 整张榜原样推**，这正是兜底能力的来源 |
| `for item_id, score in self._top_items:` | 从最热门往下遍历 | 榜单已排好序，从冠军开始 |
| `if item_id in seen: continue` | 跳过已看过的 | Level 4 坑 2，集合查 O(1) |
| `out.append((item_id, score))` | 收进结果 | 带归一化分数 |
| `if len(out) >= k: break` | 凑够 k 个就停 | 不用遍历完整张榜 |

#### 和 ItemCF 的 `recall` 对比一眼

| 维度 | **Popular.recall** | **ItemCF.recall** |
|---|---|---|
| 角色 | 兜底 / 保险栓 | 个性化主力 |
| 控制流 | 单层循环（查表取数） | 双层循环（现场累加） |
| 候选池 | 全局唯一，所有人共用 | 因用户历史而异 |
| 个性化 | ❌ 零（所有人相同，只是各自去重） | ✅ 强（每人历史不同 → 候选不同） |
| 新用户 | ✅ `seen` 默认空集 → 返回热门榜兜底 | ❌ `if not hist: return []` 束手无策 |
| 打分 | fit 阶段预算好的静态热度 | recall 现场累加亲密度（多段历史命中同一邻居就叠加） |
| 归一化时机 | fit 阶段（`c / max_p`，全局静态可提前算） | recall 末尾（`s / max_s`，分数现场算出来才知道最大值） |
| 复杂度 | `O(k + \|seen\|)` 很轻 | `O(H·K + …)` 重得多（约 50×100 次累加 + 排序） |
| 实测 Recall@200 | 36.97% | 50.15% |
| 实测 Coverage@200 | 22.29%（马太效应） | 69.89% |

> **核心结论**：ItemCF 强在"懂你"，但**前提是你得有历史**；Popular 弱在"千人一面"，但**永远有结果**。前者在"新用户"那一格交白卷，后者刚好补上——所以 `MultiRecaller` 把两者用 RRF 一融合，就得到了"既个性化、又永不空手"的候选名单。**这张对比表就是热门召回存在的全部理由——两者互补，缺一不可。**

## Level 6：升级版的热门榜

recsys-mini 实现的是最朴素的"全局静态热门"。工业界还有几个常见升级款。

### 6.1 时间衰减热门 —— 「最近火的更重要」

#### 问题：朴素热门没有"时间观念"

朴素热门 `groupby().size()` 把所有交互**一视同仁**——"上个月租了 500 次"和"上周租了 500 次"算出来热度一模一样。但显然**最近的热度更有参考价值**：上周还在火的片，这周大概率还能推；一年前火过、现在没人看的"过气爆款"，再推就是给用户添堵。

```
《某去年贺岁片》  全年累计租 5000 次，但最近一个月几乎没人租
《某本周新片》    上线才 1 周就租了 800 次
                ↑ 朴素热门：贺岁片排前面（总量大）
                ↑ 我们想要：新片排前面（正在火）
```

#### 解法：给每次交互按"年龄"打折

```
热度(i)  =  Σ_{i 的每次交互}  exp(-α · 距今天数)
```

每次交互不再"算一票"，而是算 `exp(-α · Δt)` 票——**越久远的交互，票越轻**。`α` 是衰减速度的旋钮：

| 距今天数 Δt | `exp(-α·Δt)`（取 α≈0.099，即半衰期 7 天） |
|---|---|
| 今天（0 天） | 1.00（满票） |
| 7 天前 | 0.50（半票） |
| 14 天前 | 0.25 |
| 30 天前 | ≈ 0.05（几乎不算数） |

> **半衰期视角**：把 `α` 调成"7 天前的交互只剩半票"，等价于 `α = ln2 / 7 ≈ 0.099`。想让榜单"反应更快"就调大 `α`（衰减更陡），想"更稳"就调小。

#### 和 ItemCF 时间衰减是同一个思想

> 这其实就是 [`05-collaborative-filtering_CN.md`](05-collaborative-filtering_CN.md) 里 ItemCF "推理时时间衰减" `exp(-α·Δt)` 的同款套路——**衰减因子一模一样**，只是一个用在"算物品全局热度"，一个用在"算用户对候选的兴趣分"。

#### 工程提示

- **要存时间戳**：`recsys-mini` 的 `PopularRecaller` 当前 `fit` 只数 `size()`，没用到 `ts`。要做时间衰减，得在 `fit` 时把 `train_df["ts"]` 取出来按上式加权求和。
- **要定期重算**：`exp(-α·Δt)` 里的 `Δt` 是"距今"，所以**今天的榜和明天的榜不一样**——必须周期性（天级/小时级）重新 `fit`，否则"距今"会越来越久，整张榜一起衰减失真。

### 6.2 分区热门 / 分群热门 —— 「不同人群看不同的榜」

#### 问题：一张全局榜太"粗"

全局热门榜假设"所有人口味一样"，但现实里**人群是分层的**：

```
科幻迷打开 App → 全局榜推给他《泰坦尼克号》《前任攻略》（爱情片，全站最热）
            → 他一个都不想看 → 兜底兜了个寂寞
```

全局榜被**大众口味**主导，小众群体（科幻迷、纪录片爱好者）的兜底体验很差。

#### 解法：拆成多张"小榜"

按某个维度把用户/物品分桶，**每个桶单独统计一张热门榜**：

| 分法 | 怎么分 | 例子 |
|---|---|---|
| **按类目** | 物品的标签/频道 | 科幻热榜、爱情热榜、纪录片热榜各一张 |
| **按地域** | 用户的 LBS / 注册地 | 北京热榜 vs 广州热榜（地域偏好差异大） |
| **按人群** | 年龄 / 性别 / 新老用户 | 年轻人榜 vs 中年人榜、新用户榜 vs 老用户榜 |
| **按时段** | 请求的时间 | 工作日通勤时段榜 vs 周末晚间榜 |

```
你点进"科幻"频道 → 给你看"科幻分区热榜"，而不是全站大杂烩
你在广州刷信息流 → 优先广州本地热榜
```

#### 为什么说它是"性价比之王"

> 分区热门是一种**"伪个性化"**——它不训练任何模型、不算用户向量，只是把 `groupby("item_id")` 换成 `groupby(["类目", "item_id"])` 多分一层组，**成本几乎为零**，但体验比全局热门好得多。

它还顺手缓解了 [坑 1 的马太效应](#坑-1马太效应--越热越推越推越热)：**N 张小榜的曝光名额加起来，比 1 张大榜能覆盖到更多长尾内容**（每张小榜都有自己的"头部"，等于给了更多物品出头的机会）。

#### 粒度权衡

分得越细，越贴近个性化，但**每个桶的样本越少 → 统计噪声越大**（又回到了 [6.3 小样本问题](#63-wilson-下界--贝叶斯平滑--别被小样本骗了)）。所以分区不能无限细分——通常分到"类目 / 大区 / 粗人群"这种**每个桶仍有足够交互量**的粒度为止，再细就该交给真正的个性化召回（ItemCF / 双塔）了。

### 6.3 Wilson 下界 / 贝叶斯平滑 —— 「别被小样本骗了」

#### 问题：按"比率"排序时，小样本会作弊

前面讲的都是按**计数**（租了多少次）排。但很多场景要按**比率**排——好评率、点击率（CTR）、点赞率。这时小样本会出大乱子：

```
A 片：2 个人租，2 个都好评    → 好评率 = 2/2   = 100%
B 片：1000 人租，900 好评      → 好评率 = 900/1000 = 90%
```

朴素按好评率排，**A（100%）会排在 B（90%）前面**——但 A 只有 2 个样本，这个 100% 纯属运气，**毫无统计置信度可言**。只要 A 再多两个差评，好评率立刻掉到 50%。我们真正想要的是：「**在有足够把握的前提下，这个东西的真实好评率至少有多高？**」

#### 解法一：Wilson 置信区间下界

> **核心思想**：不要用"观测到的好评率"排序，而用"**真实好评率的置信区间下界**"排序——**样本越少，下界被压得越狠**（信心打折）。

公式（`p̂` = 观测好评率，`n` = 样本数，`z` = 置信水平对应的分位数，常用 `z=1.96` 即 95% 置信）：

$$
W = \frac{\hat{p} + \dfrac{z^2}{2n} - z\sqrt{\dfrac{\hat{p}(1-\hat{p})}{n} + \dfrac{z^2}{4n^2}}}{1 + \dfrac{z^2}{n}}
$$

公式很唬人，但**直觉只有一句**：在观测好评率 `p̂` 的基础上，**减去一个随样本数 `n` 缩小的"不确定性惩罚"**。代回上面的例子：

| 片 | 观测好评率 `p̂` | 样本 `n` | Wilson 下界 `W` | 排序结果 |
|---|---|---|---|---|
| A | 100% | 2 | **≈ 0.342** | 被打到 B 后面 ✅ |
| B | 90% | 1000 | **≈ 0.879** | 稳稳排在前面 ✅ |

→ A 那个"虚高的 100%"被砍到 0.34，因为只有 2 个样本、置信度极低；B 的 90% 因为样本大、几乎不打折。**这正是我们想要的：大样本高分 > 小样本满分。**

> 这就是 Evan Miller 那篇经典文章 *How Not To Sort By Average Rating* 推广开的做法，新闻热榜、电商/应用商店评分排序里非常常用。

#### 解法二：贝叶斯平滑（更直观的"兑水"版）

Wilson 偏统计，工程上还有个**更朴素也更常用**的等价思路——**贝叶斯平滑**（也叫加性平滑 / 先验平滑）：

$$
\text{平滑好评率} = \frac{\text{好评数} + \alpha}{\text{总数} + \alpha + \beta}
$$

意思是：**先假装每个物品天生就带了 `α` 个好评和 `β` 个差评**（这个"假想的初始票"就是先验，通常取全局平均好评率）。样本越少，这几票先验占比越大，结果越被往"全局平均"上拉；样本越大，先验被真实数据淹没，几乎不影响。

举例（假设先验 `α=β=5`，相当于"每个新片先白送 5 好评 5 差评"）：

| 片 | 原始 | 平滑后 |
|---|---|---|
| A：2 好评 0 差评 | 100% | `(2+5)/(2+10)` = **58.3%** |
| B：900 好评 100 差评 | 90% | `(900+5)/(1000+10)` ≈ **89.6%** |

→ 同样把 A 从虚高的 100% 拉回到 58%，而 B 几乎不变。**贝叶斯平滑用一行除法就实现了 Wilson 的核心效果**，工程里更常见。

#### 两者对比

| | Wilson 下界 | 贝叶斯平滑 |
|---|---|---|
| 本质 | 真实比率的**置信区间下界** | 加一组**虚拟先验票**再算比率 |
| 调参 | 置信水平 `z`（如 1.96） | 先验强度 `α, β` |
| 实现 | 一个稍长的公式 | **一行除法**，最常用 |
| 直觉 | "至少有多好"（保守估计） | "把小样本往全局平均兑水" |

> ⚠️ **重要前提**：这一招**只在"按比率排序"时才用得上**。recsys-mini 当前是按**原始计数**（`groupby().size()`）排的，对应的修正是 [Level 4 坑 4](#坑-4用次数还是人数-重复交互偏差) 的"次数 vs 人数"，**不是** Wilson/贝叶斯平滑。只有当你把热门榜从"按租赁次数"改成"按好评率/点击率"排时，才需要请出本节这两位。

### 6.4 实时热门 —— 「秒级追上突发爆款」

#### 问题：离线重算永远慢半拍

前面 6.1 的时间衰减解决了"老热度该不该算数"，但它**还是离线批量重算的**——天级、最多小时级。可有些场景的热度是**分钟级**爆发的：

```
突发新闻 / 直播带货爆品 / 球赛绝杀瞬间 / 明星塌房热搜
  → 10 分钟内从无人问津冲到全站第一
  → 但你的热门榜是凌晨 3 点离线算的
  → 这波流量高峰里，它压根不在榜上 → 完美错过
```

对新闻、短视频、电商大促这类**强时效**场景，"昨晚算好的榜"约等于"过期报纸"。

#### 解法：用流式计数实时维护热度

不再"攒一天再统一算"，而是**来一条交互就更新一次计数**，榜单始终是"此刻最新"的：

```
交互事件流（Kafka/Flink）
   │  每来一条 (user, item, ts)
   ▼
滑动窗口计数器（如最近 1 小时 / 最近 10 分钟）
   │  item 的窗口内计数 +1，过期的自动减掉
   ▼
Top-N 热榜（Redis ZSET 实时维护）
   │  ZINCRBY 更新分数，ZREVRANGE 取榜
   ▼
召回时直接读 Redis → 永远是"此刻"的热榜
```

| 关键技术 | 干啥 |
|---|---|
| **流式框架**（Flink / Spark Streaming / Kafka Streams） | 消费交互事件流，做窗口聚合 |
| **滑动 / 滚动窗口** | 只统计"最近 N 分钟"，老数据自动滑出（天然带时间衰减） |
| **Redis ZSET（有序集合）** | `ZINCRBY` 实时累加分数、`ZREVRANGE` 毫秒取 Top-N，是热榜的标准载体 |
| **近似计数**（Count-Min Sketch / HyperLogLog） | 物品量极大时，用少量内存换近似热度/去重计数 |

#### 代价：为什么是 ⭐⭐⭐

> 实时热门的收益最直接（秒级追热点），但**工程代价也最高**：要搭流式管道、要维护窗口状态、要处理乱序/延迟到达的事件、要防刷量（突发热点最容易被黑产薅）。所以它通常**只用在强时效频道**（热搜、实时榜、大促会场），普通推荐位用 6.1 的天级/小时级离线热榜就够了。

### 6.5 一张表看清楚

| 升级款 | 解决什么问题 | 典型场景 | 代价 / 复杂度 |
|---|---|---|---|
| **时间衰减热门** | 老热度和新热度被一视同仁（抓不住趋势，[Level 4 坑 3](#坑-3时效性--榜单多久更新一次)） | 大多数推荐位的默认增强 | ⭐ 改 `fit` 加个 `exp(-α·Δt)` 加权 |
| **分区 / 分群热门** | 全局榜太粗、被大众口味主导，小众群体兜底体验差 | 频道页 / 分地域 / 分人群 | ⭐⭐ 多 `groupby` 一层，几乎零成本 |
| **Wilson / 贝叶斯平滑** | 按**比率**排时，小样本高分（2 人 100% 好评）虚假上榜 | 评分榜 / 好评率榜 / CTR 榜 | ⭐⭐ 一个公式 / 一行除法 |
| **实时热门（流式统计）** | 离线榜更新太慢，错过分钟级突发爆款 | 热搜 / 实时榜 / 直播 / 大促 | ⭐⭐⭐ 要搭流式管道 + Redis + 防刷 |

> **怎么选**：绝大多数项目从 **6.1 时间衰减**起步（性价比最高）；要照顾小众就上 **6.2 分区**；榜单改成按比率排了才需要 **6.3 平滑**；只有强时效业务才值得上 **6.4 实时**。它们**互不冲突，可以叠加**——比如"分地域 + 时间衰减 + 实时"组合出一张"广州本地实时热榜"。

## Level 7：热门召回的命门

热门榜小哥再勤快，也有干不了的事。下表把每个命门和"该找谁补"一并列出：

| 命门 | 表现 | 为啥 | 解药（找谁补） |
|---|---|---|---|
| **零个性化** | 给所有人推一样的东西 | 它根本不看"你是谁" | 个性化召回：ItemCF / 双塔；轻量改良用 [6.2 分区热门](#62-分区热门--分群热门--不同人群看不同的榜) |
| **马太效应** | 长尾内容永远出不了头 | 越热越推，赢者通吃（Coverage 仅 22%） | 低融合权重 + 内容召回 / Swing 捞长尾 |
| **新物品冷启动** | 刚上架的片热度=0，进不了榜 | 和 ItemCF 一样的结构性问题 | 内容召回（用标题/简介做向量）、双塔（带物品侧特征） |
| **趋势滞后** | 静态榜抓不住突发爆款 | 取决于更新频率 | [6.1 时间衰减](#61-时间衰减热门--最近火的更重要) / [6.4 实时热门](#64-实时热门--秒级追上突发爆款) |

> **所以热门召回从来不单独用**——它单跑 `Recall@200` 只有 36.97%（远低于 ItemCF 的 50.15%），但作为**兜底 + 补底**和别的召回路并行，价值无可替代。注意：表里前两个命门（零个性化、马太效应）是热门召回的**固有属性**，只能靠别的召回路互补；后两个（新物品、趋势滞后）则可以靠 Level 6 的升级款在它**自己内部**缓解。

## Level 8：在多路召回里的位置

recsys-mini 的召回路线：

```
ItemCF (权重 1.0)  ┐
                   ├─► RRF 融合 ─► Recall@200 = 50.20%
Popular (权重 0.3) ┘
```

### 各路实测对比（MovieLens-1M / LOO 切分）

| 召回方法 | Recall@10 | Recall@50 | Recall@200 | Coverage@200 |
|---|---|---|---|---|
| ItemCF | 5.29% | 20.08% | **50.15%** | 69.89% |
| **Popular（兜底）** | 4.74% | 15.48% | 36.97% | **22.29%** |
| RRF 多路融合 | 6.08% | 19.50% | 50.20% | 69.36% |

**先搞清楚两个指标在量什么**（详见 [`04-recall_CN.md`](04-recall_CN.md#2-召回的-3-个-kpi--红娘的-3-个考核)）：

| 指标 | 一句话定义 | 越高代表 |
|---|---|---|
| **Recall@K** | 用户真正喜欢的那个物品，有没有落进召回的前 K 个候选里 | **召得准**（不漏真爱） |
| **Coverage@K** | 全库有多大比例的物品，至少出现在了某个用户的候选里 | **召得广**（不只反复推那几个爆款） |

> 注意：召回阶段**只看"在不在候选集里"**，不看排第几，所以**不评 NDCG**。

#### 一个小例子（K=3，全库共 5 部片 {A, B, C, D, E}）

LOO 切分下，每个用户**留 1 个**真正喜欢的片做答案（test item），看它在不在召回的前 K 个里：

| 用户 | 真爱（答案） | 召回的 top-3 候选 | 命中？ |
|---|---|---|---|
| 小王 | **C** | [A, **C**, B] | ✅ 命中（C 在里面） |
| 小李 | **E** | [A, B, C] | ❌ 漏掉（没有 E） |
| 小张 | **A** | [A, B, D] | ✅ 命中 |

**算 Recall@3**：3 个用户里命中 2 个（小王、小张）→

```
Recall@3 = 命中用户数 / 总用户数 = 2 / 3 ≈ 66.7%
```

> 直觉：**"我给你的 3 个候选里，有没有你真正想要的那个？"** 这就是为什么召回宁可多发候选（K 大一点）也别漏——漏了后面排序再聪明也救不回来。

**算 Coverage@3**：把三个用户的候选去重并集 = {A, B, C, D} → 用到了 4 部，全库 5 部 →

```
Coverage@3 = 候选并集去重后的物品数 / 全库物品数 = 4 / 5 = 80%
```

> 直觉：**"整个片库你到底用了多少？"** 上面三人的候选始终没出现 **E**——如果换成纯热门召回，大家候选高度雷同，并集会更小、Coverage 会更低，这正是马太效应在指标上的样子。

**怎么读这张表**（逐行拆）：

1. **Popular 单看指标全面落后 ItemCF**——这很正常，它本来就不是主力。它零个性化，给所有人推同一张榜，能命中的自然只是"恰好喜欢大众爆款"的那部分用户。

2. **但它的 `Recall@10` 有 4.74%，离 ItemCF 的 5.29% 并不远**（差距仅 0.55 个百分点）——说明"大众爆款"确实能命中相当一部分用户的兴趣，**兜底质量不差**。这正是推荐系统里一条著名经验结论（Cremonesi et al., RecSys'10，见英文版 [`06-popular-recall.md`](../en/06-popular-recall.md) §10）的体现：**热门基线在 top-N 任务上是个"看似平庸、实则难缠"的对手**，新模型如果连热门都打不过，基本可以推倒重来。

3. **但 K 越大，Popular 掉队越明显**——把三列横着看：

   | | Recall@10 | Recall@50 | Recall@200 |
   |---|---|---|---|
   | ItemCF | 5.29% | 20.08% | 50.15% |
   | Popular | 4.74% | 15.48% | 36.97% |
   | **差距** | **0.55pt** | **4.6pt** | **13.2pt** |

   → K=10 时两者贴得很近，但到 K=200 时 ItemCF 反超 13 个点。原因：**热门榜就那么长，头部几十个爆款人人爱，但越往后越是"大众但你未必爱"的长尾，个性化的 ItemCF 越能在大候选量里精准补到你的小众口味**。这说明**热门召回的"有效深度"很浅**——它适合占据候选名单的前几十个保险位，不适合铺满 200 个。

4. **它的 `Coverage` 只有 22.29%（ItemCF 是 69.89%，差 3 倍）**——印证了 [Level 4 坑 1 的马太效应](#坑-1马太效应--越热越推越推越热)：热门榜来来回回就推那 22% 的爆款，**78% 的长尾内容永远进不了任何人的候选**。所以融合时只给它 `0.3` 的低权重，避免它把候选池带成"全是热门"。

5. **RRF 融合 = 1 + 0.3 > 1**——最关键的一行：把"全面落后"的 Popular 用低权重融进来，**非但没拖累 ItemCF，反而在 `Recall@10` 上从 5.29% 提到了 6.08%**（+0.79pt）：

   | | Recall@10 | Recall@200 | Coverage@200 |
   |---|---|---|---|
   | ItemCF 单路 | 5.29% | 50.15% | 69.89% |
   | **RRF（+Popular）** | **6.08%** ↑ | 50.20% ≈ | 69.36% ≈ |

   → `Recall@10` 明显提升、`Recall@200` 和 `Coverage` 几乎不变。**这就是兜底的正确姿势**：在头部用大众爆款补上 ItemCF 漏掉的那部分"从众型"兴趣（拉高浅层 Recall），同时因为权重低、又不破坏 ItemCF 主导的整体候选结构（深层指标不退化）。**1 + 0.3 真的 > 1。**

### 为什么权重是 0.3 而不是 1.0？

```
权重高 → 候选里热门占比大 → 个性化被稀释 → 体验变"千人一面"
权重低 → 热门只在"个性化不足时"悄悄补位 → 既兜了底又不抢戏
```

`popular: 0.3` 就是这个"补位但不抢戏"的平衡点——让热门榜小哥**安静地站在老挑片员身后**，只在需要时递补。

---

## TL;DR — 三句话

1. **热门召回 = 店门口的本周热租榜。**
   不看你是谁，只按全局热度从高到低排，再各自跳过看过的。`src/recall/popular.py` 36 行全实现了。

2. **它最大的价值不是指标，而是"兜底"。**
   新用户、冷启动、候选不足时，它保证系统**永远有东西可推**——这是任何个性化召回都给不了的保险栓。

3. **它的命门是马太效应（Coverage 仅 22%）和零个性化。**
   所以工业界从不单用它，而是给它一个**低融合权重**（recsys-mini 用 0.3），让它"补位但不抢戏"，和 ItemCF、双塔、内容召回并行互补。
